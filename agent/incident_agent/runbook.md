# 장애 대응 매뉴얼 (발췌)

이 문서는 Agent가 "지금 할 조치"/"근본 해결"을 지어내지 않고 인용할 수 있도록 미리 준비해 둔
사내 대응 매뉴얼 발췌본이다. 실제 운영 매뉴얼을 흉내 낸 샘플이며, 각 절은 특정 원인 유형과
연결되어 있다.

## 4.1 메모리 사용량 지속 증가 (코드 결함)

- 1차 조치: 해당 인스턴스를 재시작해 누적된 메모리를 즉시 회수한다. 재시작 전 힙 덤프를 1회
  떠서 보관한다 (`jmap -dump`).
- 재발 방지: 무한정 쌓이기만 하는 컬렉션/캐시(static Map, List 등)를 찾아 TTL 또는 최대 크기
  제한을 건다. 더 이상 쓰지 않는 레코드는 `remove`/`clear`로 명시적으로 비운다.
- 점검 포인트: 감사 로그·이력 캐시류는 특히 자주 빠뜨리는 지점이다 — 쌓기만 하고 비우는 코드가
  있는지 반드시 확인한다.

## 4.2 DB 커넥션 풀 고갈 (코드 결함)

- 1차 조치: 커넥션 풀을 재초기화하고, 풀 사이즈를 일시적으로 늘려 오버플로를 막는다.
- 재발 방지: 커넥션을 열고 반납하지 않는 경로(예외 발생 시 `close`가 스킵되는 코드)를 찾아
  try-with-resources 또는 `finally` 블록으로 교체한다.

## 4.3 동시 요청 시 재고/수량 유실 (코드 결함 — 동시성)

- 1차 조치: 의심되는 값(재고 수량 등)을 수동으로 재집계해 정합성을 맞춘다.
- 재발 방지: "읽고-계산하고-쓰는" 패턴이 원자적이지 않은 코드를 찾아 DB 레벨 락
  (`SELECT ... FOR UPDATE`) 또는 낙관적 락(버전 컬럼)으로 교체한다. 단순 `synchronized`는
  다중 인스턴스 환경에서는 효과가 없으므로 주의한다.

## 4.4 캐시 미반영 (코드 결함)

- 1차 조치: 캐시를 수동으로 비우거나 TTL을 단축해 임시로 해소한다.
- 재발 방지: 쓰기(생성/수정/삭제) 경로에 캐시 무효화(invalidate) 호출이 빠져 있는지 확인하고
  추가한다.

## 4.5 특정 입력값에서 예외 처리 누락 (코드 결함)

- 1차 조치: 해당 입력 패턴(null/누락 필드 등)을 임시로 차단하거나 기본값으로 방어한다.
- 재발 방지: null 체크 및 분기 처리를 추가하고, 테스트 케이스에 해당 입력값을 추가해 회귀를
  방지한다.

## 4.6 불필요한 재시도 폭주 (코드 결함)

- 1차 조치: 해당 배포를 롤백하거나, 사전 재시도 로직을 임시로 비활성화해 호출량을 즉시 줄인다.
- 재발 방지: 실패하지도 않은 호출을 백오프 없이 미리 여러 번 반복하는 코드를 찾아 제거하고,
  재시도가 꼭 필요한 경우에도 지수 백오프와 최대 횟수 제한을 둔다. 외부 시스템이 실제로 느리거나
  타임아웃 나는 것과 혼동하지 않도록, 재시도 호출이 코드 쪽에서 무조건 발생하는지 먼저 확인한다.
- 점검 포인트: "실패 시에만 재시도"가 아니라 "성공 여부와 무관하게 미리 여러 번 호출"하는 패턴은
  외부 시스템 문제가 아니라 코드 결함이다 — 6.1절(외부 시스템 응답 지연)과 헷갈리지 않는다.

## 4.7 로그에 민감정보 평문 노출 (코드 결함)

- 1차 조치: 해당 로그 라인을 즉시 비활성화하거나 마스킹 처리로 배포하고, 이미 쌓인 로그 파일에
  대한 접근을 제한한다 (필요 시 보안팀에 노출 범위 공유).
- 재발 방지: 카드번호·비밀번호·주민번호 등 민감 필드는 로그에 남기지 않거나 마스킹
  (`****-****-****-1234` 등) 처리한다. 코드 리뷰 체크리스트에 "민감정보 로그 노출" 항목을
  추가한다.

## 4.8 금액 계산에 부동소수점 사용 (코드 결함)

- 1차 조치: 해당 계산 결과값(적립 포인트/금액 등)을 수동으로 재계산해 오차를 보정한다.
- 재발 방지: 금액·포인트 등 돈과 관련된 값은 `double`/`float` 대신 `long`(최소 단위, 예: 원)
  또는 `BigDecimal`로 계산하도록 코드를 수정한다.

## 4.9 요청마다 스레드 생성(스레드 누수) (코드 결함)

- 1차 조치: 해당 인스턴스를 재시작해 누적된 스레드를 즉시 정리한다. 재시작 전 스레드 덤프를
  1회 떠서 보관한다 (`jstack`).
- 재발 방지: `new Thread().start()`로 매 요청마다 스레드를 새로 만드는 코드를 찾아, 크기가
  고정된 `ExecutorService`(스레드 풀)로 교체한다.

## 4.10 비멱등 재시도로 중복 처리 (코드 결함)

- 1차 조치: 최근 처리된 결제/주문 중 중복 승인·중복 청구가 발생했는지 수동으로 대조하고, 발견 시
  환불/취소 등 보정 조치를 한다.
- 재발 방지: 실패 시 같은 요청을 그대로 재시도하는 코드에 멱등성 키(idempotency key)를 부여해,
  같은 키로 두 번 요청해도 외부 시스템이 한 번만 처리하도록 바꾼다.

## 4.11 종료 조건 오류로 인한 과도한 반복 (코드 결함)

- 1차 조치: 해당 요청을 처리 중인 스레드/인스턴스를 재시작해 반복을 즉시 중단시킨다.
- 재발 방지: `while` 반복문의 종료 조건(플래그 변수)이 반복문 본문 안에서 실제로 갱신되는지
  확인하고, 누락되어 있다면 갱신 코드를 추가한다. 추가로 최대 반복 횟수 등 안전장치(guard)를
  코드에 명시적으로 둔다.

## 5.1 설정값 오류 (설정 오류)

- 1차 조치: 직전에 변경된 설정 키를 원래 값으로 되돌린다. 변경 이력(배포/설정 로그)에서
  "설정 갱신 적용" 로그를 역추적해 정확한 키·직전 값을 확인한다.
- 재발 방지: 설정 변경은 배포 파이프라인을 통해서만 반영되도록 하고, 운영 환경 설정값에는
  범위/형식 검증(validation)을 추가한다.

## 5.2 DB 커넥션 풀 크기 과소 설정 (설정 오류)

- 1차 조치: `maximum-pool-size` 설정값을 직전 값으로 되돌리고 인스턴스를 재시작(또는 커넥션
  풀을 재초기화)한다.
- 재발 방지: 커넥션 풀 크기는 배포 파이프라인의 설정 검증 단계에서 최소값(예: 5 이상)을
  강제하도록 하고, 변경 시 알림을 받도록 한다.

## 5.3 로그 레벨 설정 오류 (설정 오류)

- 1차 조치: 로그 레벨을 원래 값(INFO 등)으로 되돌려 과도한 로그 적재를 즉시 멈춘다. 이미 쌓인
  로그 파일은 디스크 용량 확보를 위해 정리하거나 보관소로 이동한다.
- 재발 방지: 운영 환경에서 TRACE/DEBUG 레벨이 실수로 적용되지 않도록, 로그 레벨 변경에는
  승인 절차를 두거나 운영 프로파일에서 최소 레벨을 강제한다.

## 5.4 쿠폰 기능 플래그 오설정 (설정 오류)

- 1차 조치: 기능 플래그(`app.order.coupon.enabled`)를 원래 값(true)으로 되돌린다.
- 재발 방지: 기능 플래그 변경 시 영향 범위(어떤 화면/API가 꺼지는지)를 사전에 점검하는 체크리스트를
  두고, 변경 로그를 모니터링에 연동한다.

## 5.5 결제 타임아웃 설정값 과소 (설정 오류)

- 1차 조치: `payment.external.read-timeout` 값을 직전 값으로 되돌린다.
- 재발 방지: 타임아웃 설정값에 하한선(validation)을 두어, 실제 외부 연동 응답 시간보다 짧은
  값이 반영되지 않도록 한다.

## 5.6 검색 모드 설정 오류(레거시 전환) (설정 오류)

- 1차 조치: `app.order.search.legacy-mode` 값을 원래 값(false)으로 되돌려 느린 구버전 검색
  경로 사용을 즉시 중단시킨다.
- 재발 방지: 레거시 경로는 가능하면 코드에서 완전히 제거하고, 남겨둘 경우에도 플래그 기본값이
  항상 신버전(빠른 경로)을 가리키도록 한다.

## 5.7 주문 최대 수량 설정값 오류 (설정 오류)

- 1차 조치: `app.order.max-quantity` 값을 원래 값으로 되돌린다.
- 재발 방지: 주문 수량 상한 같은 업무 제약값은 0 또는 비정상적으로 작은 값이 반영되지 않도록
  배포 전 검증을 추가한다.

## 6.1 외부 시스템(PG 등) 응답 지연·타임아웃 (외부 시스템)

- 1차 조치: 외부 연동사 상태 페이지를 확인하고, 재시도 간격을 늘리거나 서킷 브레이커를 수동으로
  open 상태로 전환해 연쇄 장애를 막는다.
- 재발 방지: 타임아웃 값과 재시도 정책(지수 백오프, 최대 재시도 횟수)을 점검하고, 재시도 폭주로
  이어지지 않도록 서킷 브레이커를 상시 적용한다.

## 6.2 외부 PG 응답 스키마 깨짐(역직렬화 오류) (외부 시스템)

- 1차 조치: 외부 연동사에 API 변경 여부를 문의하고, 확인 전까지 해당 연동 호출을 서킷
  브레이커로 차단해 연쇄 오류를 막는다.
- 재발 방지: 외부 응답을 역직렬화하기 전에 스키마(버전) 검증 단계를 추가하고, 실패 시 명확한
  예외로 변환해 원인 파악이 쉬운 로그를 남긴다.

## 6.3 외부 PG 서버/게이트웨이 오류 (외부 시스템)

- 1차 조치: 외부 연동사 상태 페이지에서 장애 공지를 확인하고, 자동 재시도(지수 백오프)로 일시
  오류를 흡수하면서 연동사에 문의한다.
- 재발 방지: 5xx(서버 오류/게이트웨이 오류/점검중) 응답에 대해 서킷 브레이커와 재시도 정책을
  명확히 구분해 적용한다.

## 6.4 외부 PG 레이트 리밋 (외부 시스템)

- 1차 조치: 호출 빈도를 즉시 낮추고(배치/큐잉), 외부 연동사에 요청 한도(rate limit) 상향을
  문의한다.
- 재발 방지: 429 응답에 대해서는 고정 재시도가 아니라 지수 백오프 + 지터(jitter)를 적용하고,
  호출 측에 자체 레이트 리미터를 둔다.

## 6.5 외부 PG 인증 실패 (외부 시스템)

- 1차 조치: 연동에 사용 중인 API 키/서명 키가 만료되었거나 교체되었는지 확인한다.
- 재발 방지: 인증 키 만료 전 알림을 받도록 모니터링을 두고, 키 교체 절차를 문서화한다.

## 6.6 외부 PG 간헐적 실패 (외부 시스템)

- 1차 조치: 재시도(지수 백오프)로 일시적 실패를 흡수하고, 실패율을 모니터링해 임계치를 넘으면
  서킷 브레이커를 연다.
- 재발 방지: 외부 연동 호출에는 항상 재시도와 서킷 브레이커를 함께 적용해, 간헐적 실패가
  전체 장애로 번지지 않도록 한다.
